================================================================
BeReal Data Export — Reconstruction Notes
================================================================

This document describes the parts of the BeReal data export that
matter for reconstructing your BeReals as importable photos, and
lays out a few build options.


----------------------------------------------------------------
1. WHAT'S IN THIS FOLDER (and what we care about)
----------------------------------------------------------------

Key files for reconstruction
----------------------------

posts.json        1,212 entries. One per BeReal you ever posted.
                  This is the primary source of truth for rebuilding.

memories.json     Same 1,212 entries, same timestamps. Duplicate of
                  posts.json with slightly clearer field names
                  (frontImage / backImage instead of secondary /
                  primary). Either file works; we use posts.json.

Photos/bereal/    280 image files = 140 BeReal pairs.
                  Covers 2022-07-08 -> 2022-11-24.
                  Mixed format: 75 .jpg + 65 .webp.
                  Filenames look like:
                    d2cdeec7-e18e-4166-a00f-aba9e915f785-1657272804.jpg
                  (UUID + Unix timestamp; "-secondary" suffix marks
                  the front-camera shot.)

Photos/post/      2,141 image files ≈ 1,072 BeReal pairs.
                  Covers 2022-11-25 -> 2025-04-20.
                  All .webp.
                  Filenames are short random IDs, e.g.
                    2m7OJZqbD1bgsYas.webp

Why two folders? It's a single clean cutover on 2022-11-25 when
BeReal migrated their storage backend. Before that date every
post is in bereal/; after, every post is in post/. The JSON tells
us which folder to look in for each entry, so we don't need to
guess.

Coverage check: of 2,424 image paths referenced in posts.json,
2,421 exist on disk. 3 are missing (so 3 BeReals will have one
camera unavailable -- those will be skipped with a warning).
3 files on disk are orphaned (likely deleted posts) -- ignored.

Files we don't need for this task
---------------------------------

Photos/profile/        your profile pictures (6 files)
Photos/realmoji/       reaction selfies (4,232 files)
realmojis.json         metadata for the above
comments.json          comments on posts
friends.json           friend list
friend-requests.json   pending requests
blocked-users.json     blocks
conversations/         DM history
user.json              your account info
push-*.json, terms.json  account/admin metadata


----------------------------------------------------------------
2. THE FIELDS WE USE (from posts.json)
----------------------------------------------------------------

Each entry in posts.json looks like:

  {
    "primary":   { "path": "...", "width": 1500, "height": 2000, ... },
    "secondary": { "path": "...", "width": 1500, "height": 2000, ... },
    "takenAt":   "2022-07-08T09:33:33.729Z",
    "retakeCounter": 0,
    "visibility": ["friends"],
    "caption":   "...",            (optional)
    "location":  { "latitude": ..., "longitude": ... },   (optional)
    "isLate":    true / false,      (optional)
    "berealMoment": "...Z"          (optional; the official
                                     notification time that day)
  }

Mapping to the photos:

  primary    = BACK camera  = the main shot (the big background
                              in the classic BeReal composite)
  secondary  = FRONT camera = the selfie (small inset, top-left)

The path field looks like "/Photos/<user-id>/post/2m7OJZqbD1bgsYas.webp".
Locally we ignore the user-id prefix and just use the last two
segments -- e.g. Photos/post/2m7OJZqbD1bgsYas.webp.

Timestamp: takenAt is ISO-8601 UTC, millisecond precision. This is
what we stamp into filenames and EXIF.

Location: lat/lon in decimal degrees when available. Many posts
have no location -- handle as optional.


----------------------------------------------------------------
3. RECONSTRUCTION OPTIONS
----------------------------------------------------------------

All options below:
  - read posts.json
  - load both images per entry from Photos/bereal/ or Photos/post/
  - write EXIF DateTimeOriginal from takenAt so the photos sort
    correctly on the right date in iCloud / Google Photos
  - write EXIF GPS tags from location when present
  - write the caption into XMP `dc:description` and IPTC
    `Caption-Abstract` when present (Apple Photos / Google Photos
    read those, not EXIF ImageDescription)
  - name files like:  2023-08-14_18-32-05_bereal.jpg
  - tool of choice: Python + Pillow (handles WebP and JPEG
    natively, ~150 lines total)

What differs between options is the visual layout.


Option A -- Classic BeReal (recommended)
-----------------------------------------
Recreate the look of the app: back camera fills the frame,
front camera is a small rounded-corner inset in the top-left
with a thin white border.

  +-----------------------+
  | [front]               |
  |                       |
  |                       |
  |       back camera     |
  |                       |
  |                       |
  +-----------------------+

Pros: looks like a BeReal; one file per post.
Cons: the selfie is small -- detail in the front shot is lost
      compared to viewing it standalone.


Option B -- Side by side
-------------------------
Both cameras at equal size, stitched horizontally (or stacked
vertically). One file per post.

  +-----------+-----------+
  |           |           |
  |   back    |   front   |
  |           |           |
  +-----------+-----------+

Pros: both shots fully visible; great for browsing.
Cons: doesn't look like a BeReal; wide aspect ratio is awkward
      in phone photo apps.


Option C -- Two separate files per BeReal
------------------------------------------
No compositing. For each post, output two files:
  2023-08-14_18-32-05_bereal_back.jpg
  2023-08-14_18-32-05_bereal_front.jpg

Pros: full resolution preserved for both shots; simplest code;
      photo apps will group them by timestamp.
Cons: 2x the file count (~2,400 photos); no single "BeReal"
      artifact.


Option D -- Classic composite + originals
------------------------------------------
Option A plus Option C: you get the nice BeReal-style composite
for browsing, plus the originals at full resolution for archive.

Pros: best of both worlds.
Cons: ~3x file count (~3,600 photos); uses more disk.


Recommended default
-------------------
Option A. It matches what BeReal would have given you, looks
correct in any photo app, sorts by timestamp on the right date,
carries GPS so the map view works, and keeps the file count
sensible (one photo per BeReal, ~1,212 files).

If disk space isn't a concern and you want the originals too,
go with Option D.


----------------------------------------------------------------
4. DECISIONS MADE (v1 — see README + src/rebereal/)
----------------------------------------------------------------

1. Layout: A (classic, default), plus "inverted classic" (front fills
   the frame, back is the inset) and B (side by side, horizontal) are
   implemented via the layouts/ plugin registry. C / D (separate files /
   classic-plus-originals) are architected for but not yet implemented.
   Each layout exposes a registry key (classic / inverted_classic /
   side_by_side) for --layout and a display label for the GUI dropdown.
2. Output folder: each run is wrapped in a fresh folder named
   `export` (or `export(1)`, `export(2)`, ... if `export` already
   exists in the chosen output location), resolved once per run by
   `output_dir.resolve_export_dir`. Inside that wrapper, files are
   grouped by year (2022/, 2023/, ...) via the `by_year` naming
   strategy. The wrapper is orthogonal to naming; alternative
   strategies drop into src/rebereal/naming/ + register in
   NAMING_STRATEGIES.
   Because every run targets a fresh folder and retakes are
   disambiguated by `_r{n}` (see 6), an output path can never
   collide with a pre-existing file -- so there is no overwrite /
   skip-existing logic (the former `--overwrite` flag was removed).
3. Output format: JPEG. The pipeline now validates
   `config.image_format` against an IMAGE_FORMATS registry
   (currently `{"jpeg", "jpg"}`); WebP/PNG entries can be added
   alongside JPEG-conditional gating in the metadata writers.
4. Caption: embedded via XMP `dc:description` + IPTC
   `Caption-Abstract` (Apple/Google photos surface those).
   Gated by `--no-caption` / `Config.embed_caption`. EXIF
   `ImageDescription` is intentionally not written.
5. GPS: embedded via standard EXIF GPS tags when `location`
   is present (a minority of posts). Gated by `--no-gps`.
6. Retake indicator: `_r{n}` suffix appended to the filename
   stem when `retakeCounter > 0` (avoids same-second filename
   collisions for retakes). `isLate` / `_late` suffix is not
   yet wired -- out of v1 scope.
7. Output quality: two knobs, exposed in both the CLI and GUI.
   - Resolution (`--resolution`, `Config.resolution_scale`): a
     fraction of the source size, 0.01-1.0, aspect ratio kept.
     Default 1.0 (full). Applied by downscaling the *finished*
     composite (via `media/scale_image`) rather than the source
     frames, so it stays layout-agnostic and supersamples the
     inset. Capped at 1.0 -- never upscales.
   - JPEG quality (`--jpeg-quality`, `Config.jpeg_quality`):
     1-100, default 80. Both ranges are validated in `build()`.
8. GUI: a PySide6 / Qt desktop app (src/rebereal/gui/) that wraps the
   headless core -- it imports the core, never the reverse. The whole
   interface is styled from a single centralized theme
   (gui/theme.py -> build_stylesheet(PALETTE)): a pure dark-monochrome
   palette, the native system UI font with Menlo for numerals/log, and
   a two-phase window (a landing/drop page, then a settings sidebar +
   preview/log -- see below). The palette is one dict, so light / accent
   variants drop in without touching widget code. PySide6 is an optional
   extra: `pip install -e ".[dev,gui]"`.

   Two-phase flow (gui/app.py uses a QStackedWidget):
   - Landing page (gui/landing.py): a full-window dashed drop zone with
     `Choose folder…` / `Choose .zip…` buttons in the bottom corners. You
     load a BeReal export by dropping a folder OR a `.zip`, or via either
     button. Zip extraction progress is shown inline on this page.
   - Working UI: shown only after a source loads -- the settings sidebar +
     preview/log. No source-picking controls live here; a `Restart` button
     (next to `Run`) returns to the landing page and forgets the loaded
     export (and cleans up any extracted temp dir).

   A small headless adapter (src/rebereal/ingest.py) resolves whatever you
   give it to a real directory containing posts.json: a zip is extracted to
   a temp dir on a background thread, then the rest of the pipeline runs
   unchanged against that directory. The temp dir is cleaned up on Restart
   and when the app closes. ingest.find_export_root tolerates the export
   sitting one or two folders deep (zips that expand into a wrapper folder,
   or picking the parent).

   Preview is automatic: it renders as soon as the working UI appears, and
   re-renders when a setting that affects the output changes (layout,
   resolution, JPEG quality) -- debounced ~1s so dragging a slider fires
   a single render. The preview applies the resolution + JPEG-quality
   knobs so it's a faithful "what you'll get" sample. There is no manual
   Preview button. The moment a setting changes the strip dims to ~0.3
   opacity (gui/preview.py PreviewPane.set_pending) so a stale preview
   reads as "about to change" rather than unchanged; full opacity is
   restored when the new render lands. Clicking any thumbnail opens it
   enlarged in a lightbox dialog (fit to screen; closes on click or Esc).

   Running + cancelling (gui/app.py): Run is the processing action and still
   needs an output folder picked. While a run is in flight the entire
   settings sidebar is locked and greyed (the editable controls live in one
   `_settings_panel` that is disabled + dimmed to 0.4 opacity via a
   QGraphicsOpacityEffect), since changing settings mid-run is meaningless.
   The single action button toggles Run (primary) <-> Cancel (red
   `DangerButton`) -- see `_set_run_button_mode`. Cancellation is
   cooperative: the GUI Worker sets a threading.Event and the pipeline's
   run() polls `should_cancel` before each post, stopping cleanly and
   flagging RunSummary.cancelled. A cancelled run leaves partial output on
   disk; the app then asks whether to keep or delete it (Delete does
   shutil.rmtree on the per-run export folder -- safe because that folder
   name is always freshly resolved and unique to the run).
